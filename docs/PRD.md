# 极简 macOS Mihomo 客户端项目需求文档 PRD

**版本 1.0    编制日期 2026年10月14日**

适用对象：产品、macOS 客户端开发、特权 Helper 开发、测试与发布人员。

## 1 项目目标与交付基线

开发一个面向 macOS 26 及以上、仅支持 Apple Silicon ARM64 的原生 SwiftUI 客户端。客户端为 Mihomo 提供必要的 macOS 封装和控制界面，使用主窗口与菜单栏完成 Profile 管理、网络模式切换、代理模式切换、节点选择及测速。

首版以极简、可恢复的运行行为为目标。尽可能直接使用 Mihomo 既有能力；App 只覆盖自身功能关联的配置字段，其余配置由 Profile 决定。原始 YAML 与最终运行配置分开保存。

### 1.1 已确定的关键行为

- 切换 Profile 使用 Controller API 热重载，不重启 Mihomo；失败保留原 Profile、运行配置及全局状态。

- TUN、System Proxy、Off 三选一；Rule、Global、Direct 三选一。两类模式独立，切换 Profile 时保持不变。

- 启动恢复上次状态；关闭主窗口继续运行；明确退出 App 时停止 Mihomo 并恢复系统代理。

- 内置 ARM64 Mihomo，仅手动更新；只展示当前版本，更新失败自动回滚，成功确认后删除事务中的旧版本。

### 1.2 文档约定

标记为 FR 的条目是功能要求，AC 是验收用例，TV 是技术待验证项。未最终确定的参数与实现选择列在第 12 章，不视为已确认产品决定。技术验证不得擅自增加功能或改变上述行为。

### 1.3 术语

| 术语 | 含义 |
| --- | --- |
| Profile | 一份本地 YAML 或订阅下载的 YAML，以及其独立标识与节点选择记录。 |
| 网络模式 | App 对 macOS 网络的接管方式，即 TUN、System Proxy、Off。 |
| 代理模式 | Mihomo 的 Rule、Global、Direct 出站策略模式。 |
| 已提交状态 | 操作验证成功后保存的状态；界面与下次启动以此为准。 |
| 最后可用配置 | 最近一次确认成功运行的合成配置，用于操作失败后的恢复。 |

## 2 产品范围与界面

### 2.1 范围内

| 编号 | 交付范围 |
| --- | --- |
| FR01 | macOS 26+ ARM64 原生 SwiftUI App，主窗口与菜单栏入口。 |
| FR02 | GitHub Releases 分发 DMG；App、Helper、内置可执行组件完成所需签名与公证。 |
| FR03 | 内置 Mihomo；手动检查和安装内核更新；更新事务自动回滚。 |
| FR04 | 本地 YAML、订阅 URL、多 Profile、手动更新订阅及手动重新加载。 |
| FR05 | 最小字段覆盖、API 热重载、互斥网络模式、代理模式与状态恢复。 |
| FR06 | 节点选择、单个及批量延迟测试、延迟排序与颜色提示、按 Profile 保存选择。 |
| FR07 | 登录后自动启动设置、Helper 首次授权、退出清理和必要错误提示。 |

### 2.2 范围外

不提供 YAML 编辑器、DNS 设置或编辑、规则编辑、规则管理面板、流量统计、连接管理、复杂仪表盘、Web 控制面板、云同步或账户系统。Profile 中已有 DNS、规则及其他 Mihomo 能力可由内核执行，但不因此增加 App 管理界面。

不提供自动订阅更新、自动监听本地文件、自动内核更新、历史内核版本列表或用户手动回滚。首版不扩展 Intel 支持、其他操作系统、Mac App Store 分发或 App 自动更新系统。

### 2.3 主窗口

主窗口提供当前运行状态、当前 Profile、网络模式和代理模式；提供 Profile 导入、选择、订阅更新及重新加载入口。节点区展示代理组、当前选择与延迟结果，支持节点选择、单个测速、批量测速和延迟排序。

设置区仅覆盖已确定事项：开机自启与 Mihomo 当前版本及手动更新。内核或配置正在切换时，应显示进行中状态，阻止会与该事务冲突的操作。失败提示应说明失败对象、当前仍生效的状态及可重试动作。

### 2.4 菜单栏

菜单栏提供运行状态、打开主窗口、常用 Profile 与模式切换、明确退出入口。菜单栏与主窗口共享同一状态来源；任一入口的成功操作应同步反映在另一入口，失败不得留下虚假的勾选状态。

关闭窗口与退出 App 是不同操作。关闭按钮只隐藏或关闭主窗口，不停止内核、不恢复代理；菜单栏保留并可重新打开主窗口。最终菜单布局与快捷入口数量在界面设计中落实。

## 3 Profile 管理

### 3.1 导入与保存

FR08：支持导入本地 YAML 和输入订阅 URL。订阅 URL 下载的响应必须经过 YAML 解析与当前内核兼容性验证，错误页、空响应和不可用配置不得作为有效 Profile 生效。支持保存多个 Profile，并通过稳定的 Profile 标识区分各自状态。

FR09：保存导入或下载得到的 YAML 原文，不将 App 的模式、控制接口或节点选择写回原文。为配置合成另建运行文件；原文的内容、注释与排版不因 App 控制操作被改写。订阅成功更新时，使用新下载的原文替代该 Profile 的旧原文。

### 3.2 手动动作的语义

| 动作 | 数据来源 | 对运行状态的影响 |
| --- | --- | --- |
| 导入本地 YAML | 用户选择的文件 | 新增 Profile；只有明确激活并成功加载后才成为当前 Profile。 |
| 导入订阅 URL | 用户提供的 URL | 下载、验证并保存；激活遵循同一事务规则。 |
| 手动更新当前订阅 | 重新下载该订阅 URL | 验证、合成并热重载；成功后提交文件和状态。 |
| 手动更新非当前订阅 | 重新下载该订阅 URL | 仅更新该 Profile 的文件及更新时间，不影响当前内核。 |
| 手动重新加载 | 重新读取该 Profile 的本地 YAML | 当前 Profile 重新合成并热重载；非当前 Profile 不自动激活。 |
| 切换 Profile | 目标 Profile 已保存 YAML | API 热重载；保持网络模式、代理模式与 App 设置。 |

### 3.3 文件变化与导入副本

FR10：不监听 YAML 文件变化。文件发生变化时不自动解析、不自动热重载，用户通过“重新加载”触发处理。App 内不提供 YAML 编辑能力。

本地导入是保存副本还是长期引用外部文件，以及“重新加载”读取哪一份文件，需在实现前落实（TV01）。建议使用 App 数据目录内的副本；此方案下外部原文件变化不影响已导入内容，重新加载只读取保存副本。若选择外部引用，必须落实持续访问权限与文件失效行为。

### 3.4 更新失败

FR11：当前订阅的下载、解析、验证或热重载失败，不替换最后可用原文和运行配置，不改变当前 Profile 标识。非当前 Profile 更新失败保留其旧文件。失败时给出原因并允许手动重试，不静默切换到其他 Profile。

首次无有效 Profile 时展示导入入口，保持未接管网络状态；不得创建隐含订阅或默认代理配置。订阅 URL、认证信息与 YAML 中的凭据不应出现在普通错误文案中。

## 4 配置合成与 Profile 切换

### 4.1 最小覆盖原则

FR12：合成顺序为“读取 Profile 原文 → 解析 → 应用 App 管理字段 → 生成独立运行配置 → 验证 → 加载”。字段覆盖采用明确白名单，禁止用一套固定模板替换整个 Profile。

| 类别 | 覆盖边界 |
| --- | --- |
| 代理模式 | mode 由 App 的全局 Rule、Global、Direct 状态决定。 |
| 网络接管 | tun.enable 由网络模式决定；其他 TUN 字段仅在实现既定接管能力确有必要时纳入白名单并说明原因。 |
| Controller | App 所需的本地控制地址、访问密钥等属于实现控制能力的必要字段，采用受限监听与认证。 |
| 本地代理入口 | 仅处理 System Proxy 所需的端口及监听条件；具体字段、默认值与冲突策略需验证。 |
| Profile 自有字段 | DNS、规则、代理定义、代理组及其他未列入白名单的配置保持语义不变。不得无理由覆盖整个 tun 或 dns 对象。 |

若原 Profile 无法满足所选模式且必须修改超出白名单的字段才能运行，应提示不兼容并保留原状态，不得静默重写 DNS、规则或节点。白名单与配置差异应能在开发验证中检查，且原文应保持逐字节一致。

### 4.2 热重载事务

FR13：切换前记录当前 Profile、合成配置、全局模式与节点选择；读取目标原文并按当前全局状态合成候选配置。先验证，再使用 Mihomo Controller API 加载，候选路径必须满足内核安全路径限制。

使用 PUT /configs?force=true 作为热重载接口方向。[R1] 请求成功后仍需回读运行配置、代理组和选择，确认 Controller 可用、网络模式与代理模式符合预期。恢复目标 Profile 中仍有效的选择后，提交新的当前 Profile 与持久化状态。

FR14：失败不提交新 Profile。若请求超时导致结果不明确，先核对实际运行状态；发现部分生效时重新加载最后可用配置并恢复旧选择。恢复也失败时显示实际异常状态，解除 App 的失效网络接管，不得继续显示旧状态已正常运行。

### 4.3 成功与失败的边界

普通 Profile 切换、重新加载及当前订阅更新不得主动重启内核。热重载不承诺现有连接完全连续，可能中断部分连接；Mihomo 内核更新则允许按更新事务重启。

不同配置操作必须串行提交；订阅下载可以先暂存，但不能与另一切换同时修改活动配置。最终状态保存失败不得被当作完整成功，应保留可恢复记录并提示。

## 5 网络模式与代理模式

### 5.1 网络接管模式

FR15：TUN、System Proxy、Off 为互斥状态。App 不提供 TUN 与自身系统代理同时开启的组合。显示的活动模式必须对应已经验证成功的实际接管状态。

| 模式 | TUN 状态 | App 管理的系统代理 | 主要行为 |
| --- | --- | --- | --- |
| TUN | 启用 | 不启用 | 通过特权 Helper 支持 TUN；切入前解除 App 设置的系统代理。 |
| System Proxy | 关闭 | 启用 | 使受管理的 macOS 网络服务指向 Mihomo 有效本地代理入口。 |
| Off | 关闭 | 恢复原状态 | 解除 App 的系统代理修改与 TUN 接管；不等同于 Direct。 |

这里的“恢复原状态”是恢复 App 接管前保存的系统代理值，不是简单将所有代理关闭。Off 指 App 不接管系统网络；其他软件原有代理或 Profile 中的手动监听并不因此被定义为 App 功能。Off 时内核是否继续运行列为 TV02。

### 5.2 系统代理的保存与恢复

FR16：在 App 修改系统代理前保存受影响网络服务的原设置，包含其启用状态与对应地址、端口等必要值。System Proxy 切到 TUN 或 Off，以及退出 App 时，恢复 App 负责修改的设置。重复切换不能把 App 自己设置的值当成新的原始快照。

先确认 Mihomo 代理入口可用，再启用系统代理。切换模式失败时回到上一个已提交模式，并核对 TUN 与系统代理的互斥关系。网络服务变更及其他代理软件同时修改设置时的恢复策略需通过 TV05 验证，避免覆盖外部新修改。

### 5.3 代理模式

FR17：Rule、Global、Direct 使用 Mihomo 既有语义，通过 Controller API 修改并回读确认。Rule 使用 Profile 的规则；Global 使用内核全局策略；Direct 使用内核直连策略。Direct 不关闭 TUN 或 System Proxy，Off 也不隐含改为 Direct。

### 5.4 切换 Profile 的全局不变量

FR18：无论目标 Profile 原文中的 mode 或 tun.enable 是什么，切换后都保持切换前已提交的网络模式、代理模式、开机自启设置与其他 App 设置。只切换 Profile 内容并恢复目标 Profile 自己的有效节点选择。

示例：Profile A 正以 TUN 与 Rule 运行，切换到 Profile B 后仍为 TUN 与 Rule。Profile B 的原文不被改写；生成的运行配置反映 App 全局状态。失败则仍使用 Profile A。

## 6 节点选择与延迟测试

### 6.1 代理组与节点

FR19：读取当前 Profile 加载后的代理组及节点列表，显示组内当前选择。节点选择调用内核已有控制接口，成功后回读并保存。接口拒绝、节点消失或网络失败时，不把未成功的选择写入持久化状态。

选择能力以代理组实际类型和内核支持为准。自动策略组的自动行为应保持 Profile 语义；不创建新组、不改写代理组类型、不增加 App 自动选节点算法。嵌套组与固定选择的支持边界需在 TV06 中验证。

### 6.2 按 Profile 保存选择

FR20：以稳定 Profile 标识、代理组名称和成员标识记录选择。不同 Profile 即使具有同名组或同名节点，也不能共享或串用记录。切换回某 Profile、启动 App、重新加载或更新订阅后，优先恢复仍属于相应代理组的有效选择。

节点或组已不存在时，忽略无效记录，并使用当前 Profile 与内核的有效默认结果；界面显示实际选择。不得为恢复旧选择而注入已删除节点。测试排序改变不能改变当前选中项。

### 6.3 单个与批量测速

FR21：支持单个节点及批量节点延迟测试。“测速”只表示连接延迟测试，以毫秒显示，不提供带宽或下载速度测试。批量动作作用于当前界面明确显示的节点集合，不访问非当前 Profile。

测试中、有效延迟、未测试、超时及失败必须能区分。批量测试应限制并发，逐项显示结果；某个节点失败不终止所有测试。Profile 切换后，旧测试返回不得写入新 Profile 的列表。测试 URL、超时、并发上限与集合去重方式列为 TV07。

App 测速不得静默改变节点选择。官方文档提示组级测速接口可能清除自动组的 fixed 选择，因此实现需验证或采用受控的单节点批量测试方式。[R1] 不改写 Profile 原有健康检查配置。

### 6.4 排序与颜色

FR22：提供按延迟从低到高排序；有效数值参与排序，未测试、超时及失败与有效数值分开并置后，数值相同保持稳定次序。排序只影响界面展示，不改变原 YAML 的节点顺序或组结构。

延迟使用分级颜色，并同时保留毫秒数或状态文字，避免只靠颜色判断。低延迟、一般延迟、高延迟的阈值及失败颜色在 TV07 中冻结后作为验收依据，不在 PRD 中冒充已确认数值。

## 7 生命周期与状态持久化

### 7.1 保存的数据

| 层次 | 必须持久化的内容 | 恢复规则 |
| --- | --- | --- |
| 全局 | 当前 Profile 标识、网络模式、代理模式、开机自启设置 | 恢复上次成功提交值；不采纳新 Profile 的同名默认字段。 |
| 按 Profile | 原始 YAML、来源类型、订阅 URL、各代理组有效选择 | 按稳定标识隔离；订阅地址妥善保存，选择逐项验证后恢复。 |
| 内核运行 | 当前有效内核位置与版本、最后可用合成配置 | 使用已验证版本；更新事务中保存恢复依据。 |
| 系统恢复 | 系统代理原始快照、未完成事务及清理状态 | 用于退出、崩溃后清理；不得因启动覆盖未恢复的快照。 |

FR23：启动恢复所有上次已提交的功能状态，包括各 Profile 的节点选择记录与当前 Profile 的实际选择。延迟结果属于测试展示数据，不要求当作新的持久化功能；窗口位置等界面偏好未列入首版承诺。

### 7.2 首次启动与普通启动

首次启动可直接使用 App 内置 Mihomo，无需先下载内核；无有效 Profile 时不接管网络。首次需要特权能力时执行 Helper 授权。首次网络模式、代理模式与开机自启默认值在 TV08 中落实。

普通启动先检查未完成事务与系统代理快照，再加载当前 Profile 并合成配置，启动有效内核，确认 Controller 与配置状态，恢复有效节点选择，最后启用所保存的网络接管模式。启动过程不得先将系统代理指向尚未就绪的端口。

FR24：Profile 缺失、内核启动失败或 Helper 被禁用时，保留用户意图与最后可用数据，显示实际未恢复状态，不静默选择其他 Profile。允许用户重新导入、修复授权或手动重试；不得显示“已启用”却没有有效接管。

### 7.3 开机自启与窗口关闭

FR25：提供开机自启开关，在 macOS 用户登录后自动启动 App，并执行与手动启动相同的状态恢复。设置必须反映系统注册的实际结果；系统禁止或撤销时给出可理解的提示。这里的“开机自启”不意味着用户登录前接管网络。

FR26：关闭主窗口继续运行 Mihomo 和菜单栏。重复启动 App 应回到已有实例或主窗口，避免启动第二个受管理内核或重复修改系统代理。

### 7.4 正常退出

FR27：明确退出时保存已提交状态，停止接受新的切换操作，恢复 App 修改的系统代理，关闭 TUN 并停止受管理 Mihomo，核对清理结果后完成退出。下次启动仍恢复退出前用户所选模式，不能把退出清理用的 Off 覆盖成用户偏好。

## 8 进程架构与特权 Helper

### 8.1 职责边界

| 组件 | 职责 | 约束 |
| --- | --- | --- |
| SwiftUI App | 主窗口、菜单栏、Profile、配置合成、状态保存、Controller 调用、手动更新编排 | 不将整个 App 以 root 运行；界面只展示已验证状态。 |
| 特权 Helper | 承担 TUN 与必要系统操作，支持受管理内核生命周期和清理 | 接受受限请求，校验调用方与可执行文件，不提供任意命令执行。 |
| Mihomo | 执行 Profile 中的网络能力，提供配置、节点选择和延迟测试 API | 复用内核既有功能；与 App 界面功能边界分离。 |

此表确定组件责任；Mihomo 在不同模式中的具体启动身份、Helper 通信机制与服务注册方式属于技术设计，需通过 TV03 验证。App 不得管理、终止或替换其他软件启动的 Mihomo 进程。

### 8.2 授权体验

FR28：安装或首次启用特权能力时按 macOS 正式授权流程完成 Helper 注册与用户批准。授权成功且有效后，日常 TUN 切换、Profile 热重载和受支持内核操作不得反复弹出管理员授权。

用户取消或系统拒绝授权时，不启用依赖该授权的功能，不进入反复授权循环。Helper 被系统禁用、删除或因升级需要重新批准时，显示明确状态与修复入口；不能把“一次授权”解释为永久绕过系统要求。

### 8.3 通信与执行约束

App 与 Helper 的请求必须认证调用方，限制允许的操作和文件路径。用于 root 执行的内核必须先经过来源与完整性验证，并置于不允许普通写入替换的受控位置；不能直接执行 Profile 指定的任意程序或普通可写下载路径。

Controller 使用本地受限监听与访问认证；密钥不得暴露给菜单栏文案或普通诊断信息。具体 Controller 字段属于配置白名单，不能借此开放未经要求的局域网控制功能。

### 8.4 App 异常退出

FR29：App 崩溃或被强制结束后，应由已安装的生命周期机制尽快停止其受管理 Mihomo 并恢复其系统代理修改；下次启动核对残留进程、接管状态和未完成事务。此清理能力必须经故障注入验证，不能仅依赖 App 的正常退出回调。

如果系统关机、Helper 同时被终止等情况导致即时清理不可执行，应保留可恢复记录，并在下一次可运行时完成清理。异常状态不得自动被记录为操作成功。看护机制与清理时限在 TV04 中确定；不增加对其他软件进程的看护功能。

## 9 内核更新与发布交付

### 9.1 内核更新

FR30：App 内置可用的 ARM64 Mihomo。用户主动检查 Mihomo 官方 GitHub Releases，显示发现的版本，由用户决定安装。仅手动检查与安装，不定时检查、不后台自动替换。下载资产必须匹配 macOS ARM64。[R4]

FR31：只显示当前正在使用的内核版本。无历史版本列表、版本切换或手动回滚按钮。App 包中的内置内核是首次启动资源；更新过程中暂存旧内核仅用于事务恢复，不构成版本管理功能。

### 9.2 更新事务

更新流程：下载到暂存区 → 验证文件来源、完整性、架构、可执行性与现有配置兼容性 → 保留旧内核及已提交状态 → 停止旧内核 → 启动新内核 → 回读版本、Controller、模式和节点选择并确认接管状态 → 提交新版本 → 删除事务中的旧版本。

FR32：下载、校验、替换、启动或运行确认任一步失败时，自动恢复旧内核及原配置、网络模式、代理模式和节点选择。下载阶段失败不停止旧内核；新内核验证成功之前不得删除旧版本。更新中异常退出也必须能识别并完成回滚。

内核更新允许短暂网络中断。更新与 Profile 切换互斥；更新前保存当前有效状态，更新后不得重置为 Profile 默认值。若旧内核恢复也失败，解除失效接管并明确报错。运行确认标准与观察窗口在 TV09 中冻结。

### 9.3 分发要求

FR33：正式交付为 GitHub Releases 上的 DMG，面向 macOS 26+ ARM64。DMG 内 App、Helper 与内置可执行组件须满足 Developer ID 签名及公证要求，发布流程包含签名检查、公证结果检查、票据装订与 Gatekeeper 安装验证。[R3]

发布资产应有明确版本与适用架构，提供必要安装说明以及 Mihomo 的许可证与第三方声明。发行包必须在干净的目标系统验证首次启动、Helper 授权、TUN、系统代理及退出清理。

### 9.4 更新文件与签名边界

下载更新的内核不得直接写入已签名 App 包并破坏其签名。需验证独立存储、隔离属性、Gatekeeper、root 执行校验与 Helper 信任策略（TV10）。不得假定上游 Releases 的二进制天然满足本 App 的签名、公证或完整性需求。

正式 App 更新通过发布新版 DMG 交付；本 PRD 不引入独立 App 自动更新功能。

## 10 错误恢复与一致性要求

### 10.1 失败处理矩阵

| 失败场景 | 应保持或恢复 | 用户可见结果 |
| --- | --- | --- |
| 导入或订阅响应无效 | 原 Profile 与当前运行不变 | 说明解析或兼容性错误，不保存为成功更新。 |
| 重新加载验证失败 | 旧合成配置、模式与选择 | 显示旧配置继续生效及重新加载失败。 |
| 热重载失败或结果不明 | 核对实际配置；必要时热重载旧配置 | 不提交新 Profile；恢复失败显示实际异常。 |
| 节点选择失败 | 最后成功选择 | 恢复界面选择；不写入失败记录。 |
| 单个或批量测速失败 | 当前选择与运行配置不变 | 节点显示失败或超时；其余测试继续。 |
| 模式切换失败 | 旧已提交模式及代理快照 | 核对互斥状态；失败不显示新模式已启用。 |
| 内核下载或验证失败 | 旧内核继续运行 | 当前版本不变，可手动重试。 |
| 新内核无法工作 | 自动恢复旧内核与原运行状态 | 明确显示更新失败及回滚结果。 |
| 原配置或旧内核也无法恢复 | 清理 App 的失效网络接管 | 显示不可用状态，提供针对性修复入口。 |
| 退出清理或代理恢复失败 | 保存恢复记录并重试清理 | 明确提示未完成事项；下次启动继续恢复。 |

### 10.2 状态与文件的一致性

FR34：候选文件、当前文件、最后可用文件与运行状态分开处理。写入采用可恢复的原子提交方式，防止中途断电或崩溃造成半份 YAML、半份状态或丢失回滚内核。仅在成功确认后更新当前 Profile、当前版本与上次状态。

API、进程操作、下载和测速必须有明确超时与进行中状态；界面不因这些操作阻塞。失败文案必须区分操作失败、旧状态仍有效与恢复也失败，不能统一误报为“连接成功”或“网络正常”。

### 10.3 隐私与诊断

Profile、订阅地址及状态保存在本机。错误定位仅保留本功能所需诊断信息，并对订阅凭据、节点认证信息和 Controller 密钥脱敏；不新增遥测、流量统计或日志分析面板。内核可用性验证不等同于承诺所有网站或节点必然可达。

## 11 功能验收标准

每项验收必须记录测试配置、目标系统、实际结果与失败注入方式。下表与后续验收共同构成首版交付条件；涉及 TV 参数的用例须先冻结对应参数。

| 编号 | 场景与操作 | 通过标准 |
| --- | --- | --- |
| AC01 | 在 macOS 26+ ARM64 干净环境安装 DMG | 签名、公证与 Gatekeeper 验证通过；无需先下载内核即可进入 App。 |
| AC02 | 打开主窗口和菜单栏并切换状态 | 两个入口显示一致；关闭窗口后菜单栏、Mihomo 与当前接管继续工作。 |
| AC03 | 首次启用特权能力后连续切换 TUN | 仅按首次系统流程授权；授权有效后不重复要求管理员批准。 |
| AC04 | 取消授权或系统禁用 Helper | 依赖特权的操作不生效；显示真实状态与修复入口，不循环弹窗。 |
| AC05 | 导入本地 YAML 与订阅 URL | 两类来源均保存有效 Profile；无效 YAML、空响应与错误页被拒绝。 |
| AC06 | 导入多个 Profile 并进行模式和节点操作 | 原文逐字节保持；合成配置仅允许白名单字段变化，DNS 与规则语义保持。 |
| AC07 | 修改 YAML 后保持 App 运行 | 不会自动重新加载；手动重新加载按 TV01 冻结的数据来源生效。 |
| AC08 | 手动更新非当前订阅 | 该 Profile 文件更新；当前 Profile、内核进程、模式和选择保持不变。 |
| AC09 | 更新当前订阅及手动重新加载 | 经验证后 API 热重载；内核进程未重启；有效选择恢复。 |
| AC10 | 目标 Profile 带不同 mode 与 tun.enable | 切换后仍保留原全局网络模式、代理模式及 App 设置。 |
| AC11 | 热重载成功、请求失败与请求超时分别测试 | 成功才提交；失败不更换当前 Profile；超时核对实际状态并恢复，不能仅看 HTTP。 |
| AC12 | 在三个网络模式间逐一切换 | TUN 与 App 系统代理始终互斥；Off 清除 App 接管并恢复原代理设置。 |
| AC13 | 分别切换 Rule、Global、Direct | 内核回读与界面一致；Direct 不自动关闭网络接管，Off 不自动改变代理模式。 |
| AC14 | 设置预存系统代理后使用 App 并退出 | 原代理启用状态、地址和端口等正确恢复，不简单清零；Mihomo 停止。 |
| AC15 | 模式切换过程中注入内核或系统设置错误 | 不提交新模式；恢复旧模式或显示清理后的实际失败状态。 |
| AC16 | 两个 Profile 含同名组和同名节点，各选不同成员 | 切回各自 Profile 后恢复独立选择，不串用；只保存成功选择。 |
| AC17 | 订阅更新移除曾选节点或整个组 | 仅恢复仍有效成员；无效记录被跳过，界面显示实际有效选择。 |
| AC18 | 单个及批量测试，包含成功、超时和失败节点 | 显示毫秒或明确状态；失败不阻断其他节点；测试不改变原选择。 |
| AC19 | 延迟排序且测试中切换 Profile | 有效值升序、异常置后、相同值次序稳定；旧测试不污染新列表。 |
| AC20 | 观察延迟颜色与排序后的选中状态 | 颜色符合 TV07 冻结阈值且有文字；排序不修改 YAML 或选中节点。 |
| AC21 | 分别以 TUN、System Proxy、Off 退出后重开 | 恢复上次 Profile、全局模式与有效选择；退出清理不会覆盖用户模式偏好。 |
| AC22 | 启用登录自启并重新登录，随后关闭自启 | 自启按同一启动流程恢复；关闭后不再注册自启；系统拒绝时准确提示。 |
| AC23 | 重复启动 App 或当前 Profile 缺失 | 不产生第二个受管理内核；缺失时不静默换 Profile 或显示接管成功。 |
| AC24 | 手动检查并安装兼容内核更新 | 显示版本后由用户安装；重启并恢复配置和模式；确认成功才删除事务旧内核。 |
| AC25 | 注入下载、校验、新内核启动及确认失败 | 下载失败不停止旧内核；其余失败自动恢复旧内核与原状态，显示回滚结果。 |
| AC26 | 更新中强制结束 App 后重新启动 | 识别未完成事务并恢复可用版本；不会丢失唯一可用内核。 |
| AC27 | 检查内核管理与后台更新行为 | 只显示当前版本，无历史列表和手动回滚；没有自动内核或订阅更新任务。 |
| AC28 | 强制结束 App，再测试 Helper 同时退出的恢复 | 按 TV04 验证 App 崩溃清理；无法即时清理时下次启动能识别并恢复残留状态。 |
| AC29 | 故障注入最后可用配置恢复也失败 | 清理失效接管，保留修复数据并显示真实异常，不能误报旧状态仍正常。 |
| AC30 | 检查所有界面、配置差异和敏感错误输出 | 无 DNS 或规则编辑、流量统计等范围外入口；原文保留；凭据与密钥不泄露。 |

### 11.1 验收记录要求

对热重载记录前后进程标识和运行配置；对代理恢复记录网络服务设置快照；对内核更新记录新旧版本、故障阶段及清理结果。节点测试使用可控成功与失败样例，不能将真实节点偶发不可达直接视为客户端功能失败。

所有范围内功能及错误恢复用例通过后交付。发现平台或内核限制时，应先完成相应 TV 结论并更新技术设计，不能未经产品变更流程以重启替代 Profile 热重载，或以扩大 DNS、规则配置来规避问题。

## 12 技术待验证项与开发交付

以下事项需要在对应功能实现前形成结论。结论说明验证方法、适用版本、参数或方案、限制与对验收的影响；如果无法满足已确认行为，必须提出明确的需求变更，不得在实现中静默降级。

| 编号 | 待验证事项 | 应形成的结果 |
| --- | --- | --- |
| TV01 | 本地文件副本或外部引用；重新加载来源；相对路径资源 | 明确数据源、访问权限与丢失行为，保证外部资源路径处理不改写原文。 |
| TV02 | Off 状态是否保持内核运行 | 建议保留内核供控制与测速；确认后明确 UI、启动与恢复行为。 |
| TV03 | Helper 注册、调用认证、内核启动身份和生命周期归属 | 验证 macOS 26+ 的正式系统授权机制、后续免反复授权及最小权限。[R2] |
| TV04 | 崩溃清理、Helper 退出、超时与未完成事务恢复 | 故障注入证明正常与异常清理边界；冻结清理时限和恢复机制。 |
| TV05 | 系统代理接口、网络服务变化和第三方并发修改 | 定义快照粒度、恢复判定、互斥切换和失败补偿方式。 |
| TV06 | API 热重载一致性、节点组类型、内核缓存与路径限制 | 验证失败是否部分生效；明确回读与回滚办法、选择恢复和缓存隔离。[R1] |
| TV07 | 测速 URL、超时、并发、批量范围与颜色阈值 | 冻结可测试参数；确认测速不清除 fixed 选择，排序不会改变组语义。 |
| TV08 | 首启默认值与 App 字段覆盖白名单 | 冻结默认模式、自启默认值和必要监听字段；TUN 无需扩大 DNS 管理。 |
| TV09 | ARM64 资产选择、版本兼容与更新成功判定 | 定义校验、配置预验证、运行观察窗口及失败自动回滚边界。[R4] |
| TV10 | 下载内核的签名、隔离属性、可执行文件存储和许可 | 验证正式发布与更新后执行安全，不破坏 App 包签名；确认许可证义务。[R3][R4] |

### 12.1 开发交付物

交付 SwiftUI App 与 Helper 源码、可复现构建及签名公证流程、GitHub Releases DMG、安装说明、字段覆盖白名单、状态与事务恢复设计、TV 验证结论以及 AC 验收记录。模块可按界面、Profile、配置合成、Controller、状态存储、Helper、内核更新及发布组织。
